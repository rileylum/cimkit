# Testing Approach — arcgis-cicd

## Context and constraints

Testing a tool that publishes services to ArcGIS Enterprise is harder than testing ordinary software because:

- The full integration path (SD → Portal → published service) requires a licensed ArcGIS Enterprise instance
- A licensed isolated test environment is not currently available
- ArcGIS Pro is required to generate "known-good" reference artefacts, and is only available on Windows

The testing strategy is therefore tiered: maximise what can be validated without any ArcGIS dependency, and use the existing dev Enterprise environment (`arcgis-enterprise-latest.dev.geoplex.com.au`) conservatively for integration validation.

We have one significant advantage: the reverse engineering work produced a complete set of reference artefacts (`.aprx`, `.msd`, `.sddraft`, `.sd`, publish logs) generated by ArcGIS Pro from a known input. These form the golden master for all unit-level tests.

---

## Tier 1 — Unit tests (no ArcGIS, no network)

Everything in the SD generation pipeline is JSON manipulation, XML templating, and file packaging. All of it is unit-testable in isolation using the captured reference artefacts as fixtures.

### SD generation pipeline

Each transformation step has a known input and a known output from the reference artefacts. Test each in isolation:

| Step | Input fixture | Expected output | What to assert |
|---|---|---|---|
| aprx → Map.msd | `simple.aprx` | `Map.msd` | All `map/*.json` files byte-identical; JSON pretty-printed; `GISProject.json` has layout view |
| Map.msd → Updated_Map.msd | `Map.msd` | `Updated_Map.msd` | Layout view removed from `GISProject.json`; `groundElevationSurfaceLayer` removed from `map/map.json`; layout nodes removed and IDs renumbered in `Index.json`; metadata file replaced; connection strings rewritten |
| CIM → `Updated_Map.mapx` | layer JSON files from aprx | `Updated_Map.mapx` | Type is `CIMMapDocument`; `layerDefinitions` contains all layers from the aprx map; `tableDefinitions` present |
| sddraft → `manifest.xml` | `Map.sddraft` | `manifest.xml` in SD | `State` changed to `esriSDState_Staged`; `InPackagePath` values filled; database `OnPremiseConnectionString` and `InPackagePath` consistent |
| service config → `serviceconfiguration.json` | `Map.sddraft` SVCConfiguration section | `serviceconfiguration.json` | Service name, type, capabilities, and properties match sddraft |
| CIM → `featureserveritemdata.json` | layer JSON files from aprx | `featureserveritemdata.json` | Renderer type matches CIM layer renderer; field names match layer field definitions; layer IDs match |
| CIM + ogr → `featureserver.json` | layer JSON files + `simple.gdb` | `featureserver.json` | Field names, types, and geometry types match; extents are within tolerance of reference |
| esriinfo generation | service title, tags, description | `esriinfo/*.xml`, `item.pkinfo` | Title, tags present; guid stable for same inputs |
| SD packaging | all generated files | valid 7-zip archive | Archive opens without error; all expected paths present; file count matches reference |

### Roundtrip equivalence

The strongest unit-level test: generate an SD from `simple.aprx` using the headless tool, then compare it against the ArcGIS Pro-generated `Map.sd`.

The comparison cannot be byte-identical (7-zip compression is non-deterministic, JSON key ordering may differ, timestamps will differ). The comparison should be **semantic**:

- Same set of files at the same internal paths
- JSON files parse to equivalent structures (ignoring key order)
- XML files parse to equivalent DOM trees
- Binary files (`cd/` GDB, thumbnail PNG) are byte-identical

A `compare_sd(generated, reference)` function that walks both archives and reports differences is the most useful test fixture. This is directly analogous to the `compare` function in aprx-tools.

### ogr extent extraction

Test that `GetExtent()` returns the correct bounding box for each layer in `simple.gdb`, then that the reprojected extent falls within expected bounds. No ArcGIS required — just GDAL/ogr.

### Connection string rewriting

Test that `workspaceConnectionString` values are correctly rewritten from aprx-relative to staging-folder-relative paths, and that the inverse (resolving the absolute path) round-trips correctly. Edge cases: UNC paths, paths with spaces, paths with non-ASCII characters.

## Tier 2 — Integration tests against dev Enterprise

These tests validate that the Portal REST API accepts the SD and publishes successfully. They run against `arcgis-enterprise-latest.dev.geoplex.com.au` and require valid credentials.

**These tests modify live state.** They should:
- Use a dedicated test service name prefix (e.g. `arcgis_cicd_test_*`)
- Clean up after themselves (delete the published item and service)
- Not run on every commit — run on PR merge or manually triggered

### SD upload and publish

- Upload the headless-generated SD to Portal via `POST /sharing/rest/content/users/{user}/addItem`
- Trigger publish via `POST /sharing/rest/content/items/{id}/publish`
- Poll for completion
- Assert: job status is `completed`, not `failed`
- Assert: returned service URL is reachable and returns HTTP 200
- Assert: `GET /services/Map/FeatureServer?f=json` returns the expected layer names and field count
- Clean up: delete portal item and service

### Overwrite

- Publish a service
- Generate a second SD with a minor change (e.g. description update)
- Overwrite via `esriServiceDefinitionType_Replacement` in the manifest
- Assert: item ID is unchanged (downstream consumers not broken)
- Assert: service is still reachable immediately after overwrite
- Clean up

### Failure handling

- Upload a deliberately malformed SD (missing `manifest.xml`)
- Assert: Portal returns a structured error, not a 500
- Assert: the tool surfaces the error cleanly rather than timing out

### Health check

- After publish, call the tool's health check function
- Assert: it returns healthy for a correctly published service
- Assert: it returns unhealthy for a stopped service (stop the service via REST Admin API, then check)

## Tier 3 — Tests requiring a licensed isolated environment

These cannot currently run. Documented here so they can be implemented when a proper test environment becomes available.

### Clean-state publish

Verify a first-time publish against an Enterprise instance with no pre-existing services. Ensures the tool does not rely on any state left by a previous publish.

### Rollback

- Publish a service (version 1)
- Overwrite with a breaking change (schema change that would corrupt dependent maps)
- Trigger rollback to version 1
- Assert: service is restored to version 1 state
- Assert: dependent items are still functional

### Multi-environment promotion

- Publish to dev with dev connection strings
- Promote to UAT with UAT connection strings substituted
- Assert: UAT service references UAT data source, not dev
- Assert: dev service is unchanged

### Version compatibility

- Test against ArcGIS Enterprise 11.x (current)
- Test against ArcGIS Enterprise 10.9.1 (last of the 10.x line)
- Assert: SD generated against 11.x is rejected by 10.9.1 with a clear version error, not a silent failure

### Concurrent publish safety

- Trigger two simultaneous publish operations for the same service name
- Assert: second operation fails cleanly rather than corrupting the service

## Reference artefact fixtures

The following files captured from the ArcGIS Pro publish of `simple.aprx` should be committed to `tests/fixtures/` as the golden master for Tier 1 tests:

```
tests/fixtures/simple/
├── simple.aprx                          ← source project
├── simple.gdb/                          ← source data
├── arcgispro_output/
│   ├── Map.msd                          ← original MSD (aprx extract)
│   ├── Updated_Map.msd                  ← processed MSD (layout stripped)
│   ├── Map.sddraft                      ← service definition draft
│   ├── Map.sd                           ← final staged SD (ArcGIS Pro reference)
│   ├── Map_PublishResults.json          ← layer/field mapping
│   └── SharingInfo.json                 ← sharing metadata
└── sd_exploded/                         ← Map.sd unpacked for easy diffing
    ├── manifest.xml
    ├── serviceconfiguration.json
    ├── p30/
    ├── servicedescriptions/
    └── esriinfo/
```

The `sd_exploded/` tree gives unit tests easy access to individual files without needing 7-zip in every test.

## What "done" looks like without a licensed isolated environment

With only Tier 1 and Tier 2 available, the tool can be considered ready for real-world use when:

1. All Tier 1 tests pass — the generated SD is semantically equivalent to the ArcGIS Pro reference
2. The Tier 2 publish test passes against dev Enterprise — Portal accepts and publishes the generated SD
3. The Tier 2 overwrite test passes — item ID is preserved on overwrite
4. The Tier 2 health check test passes — the tool can determine whether a published service is healthy

That combination validates the full publish pipeline end-to-end. The Tier 3 gaps (rollback, promotion, version compatibility, concurrency) are real risks, but they are risks in the deployment orchestration layer, not in the SD generation layer — which is the harder and more novel part of the work.
